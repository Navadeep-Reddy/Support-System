# AI Support Agent — API Contract

This document defines the frontend/backend interface for the scope in `SPEC.md`. FastAPI and Pydantic implement these contracts and expose generated OpenAPI documentation at `/docs` and `/openapi.json`. Examples are illustrative; IDs and timestamps in real responses are generated by the backend.

## 1. Conventions

- Base URL: `http://localhost:8000` in local development; configure the frontend through `VITE_API_BASE_URL`. Paths below are relative to this URL, without an additional prefix.
- JSON request and response bodies use `snake_case`. Requests with a body use `Content-Type: application/json`. IDs are UUID strings. Timestamps are ISO 8601 UTC; money is serialized as a decimal string, e.g. `"15.00"`, with an explicit currency.
- Non-streaming HTTP. The chat endpoint returns when the graph completes, fails or pauses for approval; no connection remains open awaiting a customer decision.
- Use a backend-controlled demo session (recommended transport: signed, HTTP-only session cookie). Resolve customer identity on the server for every protected endpoint. Frontend sends credentials on requests; configure CORS for the explicit frontend origin (default `http://localhost:5173`), not a wildcard. Use local HTTP cookie settings in development; use HTTPS and secure cookies in a real deployment. The signing secret stays on the backend. Demo selection is not real authentication; no passwords or registration are required.
- Only demo customer listing and login are public; logout is safe to repeat. The knowledge management interface is available to demo sessions under the explicit demo administration assumption, not a production RBAC model.
- Do not accept `customer_id`, `thread_id`, raw graph state or tool execution parameters from the client except the explicit demo profile selection at login. Scope conversations, messages, feedback and approvals to the session owner. Return 404 for a nonexistent or other customer's resource.
- List endpoints return `{ "items": [...] }`. No pagination is required for the small demo dataset. Reject unknown fields on action decisions and other mutation inputs to avoid accidental privilege-bearing parameters.

## 2. Shared response types

The following TypeScript shapes describe the wire format. Backend schemas must validate equivalent types. `UUID`, `Timestamp` and `DecimalString` are string aliases.

```ts
type UUID = string;
type Timestamp = string;
type DecimalString = string;

type Customer = { id: UUID; handle: string; display_name: string };
type Conversation = {
  id: UUID; title: string; created_at: Timestamp; updated_at: Timestamp;
};
type Citation = {
  article_id: UUID; chunk_id: UUID; article_title: string; section: string;
};
type Feedback = {
  rating: "positive" | "negative";
  comment: string | null;
  updated_at: Timestamp;
};
type RunStatus = "running" | "waiting_for_approval" | "completed" | "failed";
type ApprovalStatus = "pending" | "approved" | "rejected" | "executed" | "failed";
type ResetResult = {
  request_id: UUID; status: "requested"; reset_url: string; simulated: true;
};
type ApprovalCard = {
  action_id: UUID;
  action_type: "request_password_reset";
  status: ApprovalStatus;
  account_display_name: string;
  created_at: Timestamp;
  decided_at: Timestamp | null;
  result: ResetResult | null;
};
type Message = {
  id: UUID;
  conversation_id: UUID;
  run_id: UUID | null;
  role: "user" | "assistant" | "action";
  content: string | null;
  created_at: Timestamp;
  citations: Citation[];
  approval: ApprovalCard | null;
  feedback: Feedback | null;
};
type Run = { id: UUID; status: RunStatus; conversation_id: UUID };
type ApiError = { code: string; message: string; retryable: boolean };
type TurnResponse = {
  run_id: UUID;
  conversation_id: UUID;
  status: "completed" | "waiting_for_approval" | "failed";
  messages: Message[];
  pending_approval: ApprovalCard | null;
  error: ApiError | null;
};
```

`action` is a presentation role for deterministic approval cards, never an LLM message role. It can be derived from an existing stored card reference; it does not require another table. User and assistant messages contain text; assistant messages may include validated citations and feedback. Action messages contain a card and no model-authored authorization content. All messages use stable IDs. The backend orders messages by persisted sequence (or timestamp plus stable tie-breaker). Citations are snapshots of validated retrieved sources, not promises that a later-edited/deleted article still contains the same text. A feedback object is present only on an assistant response with feedback.

`TurnResponse.messages` contains the visible messages belonging to the run, including any previously returned messages for that run with updated card status. The frontend upserts by message ID, not blindly appending. History is the authoritative complete conversation view. `pending_approval` is present only while waiting. An approved but not yet executed card is not a success. A failed run may contain an executed card with a reset result if the mutation succeeded but final language generation failed.

## 3. Demo session

| Method | Path | Request | Success |
| --- | --- | --- | --- |
| GET | `/demo/customers` | None | 200 `{items: Customer[]}` |
| POST | `/demo/login` | `{customer_id: UUID}` | 200 `Customer`, establishes session |
| POST | `/demo/logout` | None | 204, clears session |
| GET | `/me` | None | 200 `Customer` |

List exactly the seeded Alex and Taylor profiles, returning only safe display fields. Login validates that the chosen profile exists, replaces any previous session, and does not accept arbitrary profile attributes. The frontend clears cached account/conversation data when switching profiles or logging out. `GET /me` returns 401 without a valid session. This public profile selector is intentionally impersonable in the demo; ownership checks constrain resources within the selected session, not access to the real-world identity of a person.

## 4. Conversations and history

| Method | Path | Request | Success |
| --- | --- | --- | --- |
| GET | `/conversations` | None | 200 `{items: Conversation[]}` |
| POST | `/conversations` | `{title?: string}` | 201 `Conversation` |
| GET | `/conversations/{id}/messages` | None | 200 `HistoryResponse` |

```ts
type HistoryResponse = {
  conversation: Conversation;
  messages: Message[];
  active_run: Run | null;
  pending_approval: ApprovalCard | null;
};
```

New conversations default to `New conversation` if no title is supplied. The backend may set a short title from the first user message without an extra LLM call. Lists are ordered by most recently updated first. History includes the entire persisted user-visible transcript, not just the subset provided to the model. Resolved cards remain visible. If an active run is present, the client disables message submission in that conversation. If a card is pending, show its Confirm/Cancel controls; if a run is running, the client can refresh history to observe completion. No conversation deletion, renaming endpoint or cross-conversation memory is required.

## 5. Chat

### POST `/conversations/{id}/chat`

Request:

```json
{"message":"What is my current subscription?"}
```

Require a nonblank string within configured input/context limits. Backend validates ownership and atomically reserves the sole active run for this conversation, stores the user message, constructs context according to `SPEC.md`, and invokes the agent using the run ID as LangGraph thread ID. The customer never supplies the run ID. No API endpoint directly exposes the agent's tools.

Return 200 with `TurnResponse` for accepted executions, including a graph-level failed outcome. Use ordinary HTTP errors for requests rejected before a run is accepted (see Section 9).

| Status | Client behaviour |
| --- | --- |
| `completed` | Upsert messages, show answer and citations, enable chat input. |
| `waiting_for_approval` | Upsert messages and card; render approval controls and keep chat input disabled. |
| `failed` | Upsert messages, display safe error and any committed operation outcome; allow a new turn once no run is active. |

Example completed response (illustrative UUIDs):

```json
{
  "run_id":"00000000-0000-4000-8000-000000000010",
  "conversation_id":"00000000-0000-4000-8000-000000000001",
  "status":"completed",
  "messages":[
    {
      "id":"00000000-0000-4000-8000-000000000011",
      "conversation_id":"00000000-0000-4000-8000-000000000001",
      "run_id":"00000000-0000-4000-8000-000000000010",
      "role":"user","content":"What is my current subscription?",
      "created_at":"2026-01-01T12:00:00Z","citations":[],"approval":null,"feedback":null
    },
    {
      "id":"00000000-0000-4000-8000-000000000012",
      "conversation_id":"00000000-0000-4000-8000-000000000001",
      "run_id":"00000000-0000-4000-8000-000000000010",
      "role":"assistant","content":"You have an active Pro plan at $15 per month.",
      "created_at":"2026-01-01T12:00:02Z","citations":[],"approval":null,"feedback":null
    }
  ],
  "pending_approval":null,"error":null
}
```

If a network request times out, reload history before submitting again. Do not automatically resend a chat turn. Concurrent submissions to the same conversation return 409. No streaming, websockets or background job service is needed.

## 6. Password-reset approval

### Pending action

When the agent selects `request_password_reset`, the tool's backend preparation path validates the session, persists an immutable pending action and pauses the run before creating any reset record. The chat response has `status: "waiting_for_approval"` and a `pending_approval` object, also referenced by a visible action message.

Example pending approval object (within the turn response):

```json
{
  "action_id":"00000000-0000-4000-8000-000000000020",
  "action_type":"request_password_reset",
  "status":"pending",
  "account_display_name":"Alex",
  "created_at":"2026-01-01T12:01:00Z",
  "decided_at":null,
  "result":null
}
```

React renders the fixed title **Confirm password reset**, the selected account display name and the fixed explanation **Create a simulated password-reset request for this account. Your password will not change.** Buttons: **Confirm** and **Cancel**. Do not generate the confirmation text or operation details using the model. Do not display arbitrary HTML from an action payload.

### POST `/approvals/{action_id}`

Request (only allowed field):

```json
{"approved":true}
```

`false` rejects the action. Success: 200 `TurnResponse` with the updated card and the agent's continuation response (or another valid pending action if one is explicitly proposed within execution limits). The backend resolves the owned action and run, binds the decision to the stored operation, validates the pending status and serializes concurrent decision submissions. Resume the original checkpoint using the original run/thread ID, or use the documented database-backed continuation fallback. Never execute a fresh action based on client-supplied arguments.

- Approval: revalidate ownership and execute the stored action transactionally; create exactly one reset record per action ID and persist its result with the approval execution status. Return the actual result to the model.
- Rejection: persist the rejection, create no reset record, and return a rejection outcome to the model. A rejection does not authorize a retry or automatic replacement action.
- Repeated decision: return the recorded outcome if available and consistent, or 409 `APPROVAL_RESOLVED`; never execute twice. A concurrent in-progress decision may return 409 `RUN_ACTIVE`. On ambiguous transport failure, reload history to inspect the real outcome.
- If the final explanatory model call fails after execution, preserve the executed card/result and report an honest failed run; do not imply that the reset was rolled back.

Example executed result inside an approval card:

```json
{
  "request_id":"00000000-0000-4000-8000-000000000021",
  "status":"requested",
  "reset_url":"https://example.invalid/reset/00000000-0000-4000-8000-000000000021",
  "simulated":true
}
```

Display the link clearly as a simulated, non-operational demo link, preferably copyable text. No real reset page, email delivery, OTP or password change. A rejected card has status `rejected`, no reset result, and no active buttons.

## 7. Response feedback

### PUT `/messages/{id}/feedback`

```json
{"rating":"negative","comment":"The explanation was unclear."}
```

- `rating`: required, `positive` or `negative`.
- `comment`: optional nullable string; omission or null means no comment.
- 200 `Feedback` with the current rating/comment and update timestamp.
- Verify the message is an assistant response owned by the active customer. Return 404 for missing or foreign messages, 422 for a non-assistant message or invalid rating.
- Upsert one feedback record per customer/message pair; submitting again updates rather than duplicates it. The history response includes the stored feedback for rendering. No separate feedback analytics UI is required.

## 8. Knowledge management

```ts
type ArticleInput = { title: string; category: string; body: string };
type ArticleSummary = {
  id: UUID; title: string; category: string;
  created_at: Timestamp; updated_at: Timestamp;
};
type Article = ArticleSummary & { body: string };
```

`body` is Markdown. Title, category and body must be nonblank. Reject sections exceeding the configured heading-based chunk limit, including metadata; do not silently truncate. Render Markdown safely without executing embedded HTML or scripts.

| Method | Path | Request | Success |
| --- | --- | --- | --- |
| GET | `/knowledge/articles` | None | 200 `{items: ArticleSummary[]}` |
| GET | `/knowledge/articles/{id}` | None | 200 `Article` |
| POST | `/knowledge/articles` | `ArticleInput` | 201 `Article` |
| PUT | `/knowledge/articles/{id}` | `ArticleInput` (full replacement) | 200 `Article` |
| DELETE | `/knowledge/articles/{id}` | None | 204 |

Example create/update body:

```json
{
  "title":"Refund policy",
  "category":"billing",
  "body":"## Eligibility\nSuccessful initial payments may qualify within 14 days. Renewals are excluded."
}
```

Create/update completes only after all required embeddings have been generated and the article/chunks have been committed atomically. Return validation or indexing errors without publishing partial data. Update failure preserves the previous article and chunks. Delete removes the article and chunks atomically. Embeddings and internal chunk indexing are not exposed through public CRUD responses. The frontend can open citation article links using the existing article detail endpoint; if deleted, show the saved citation label with an unavailable-source notice. No direct vector search or embedding endpoint is necessary for the frontend.

## 9. HTTP error format

Rejected HTTP requests use a consistent envelope (including FastAPI request validation errors, via an exception handler):

```json
{
  "error": {
    "code":"RUN_ACTIVE",
    "message":"Finish the current turn before sending another message.",
    "retryable":false
  }
}
```

Optional `details` may contain safe field validation information. Never include credentials, raw exceptions, SQL or graph checkpoints. The following codes are proposed concrete defaults; keep backend/frontend in sync and document any implementation refinements in OpenAPI.

| HTTP | Code | Meaning |
| --- | --- | --- |
| 401 | `SESSION_REQUIRED` | No valid demo session |
| 404 | `NOT_FOUND` | Resource absent or not owned by this session |
| 409 | `RUN_ACTIVE` | Conversation already running or awaiting approval |
| 409 | `APPROVAL_RESOLVED` | Approval already decided or no longer pending |
| 422 | `VALIDATION_ERROR` | Invalid request fields or values |
| 422 | `SECTION_TOO_LARGE` | KB section exceeds chunk budget |
| 503 | `PROVIDER_UNAVAILABLE` | Transient AI/embedding provider failure after bounded retries |
| 503 | `DATABASE_UNAVAILABLE` | Temporary persistence failure |
| 500 | `INTERNAL_ERROR` | Unexpected application error |

Once a chat/approval run is accepted, use the `TurnResponse` status/error for recoverable graph failures and retain visible outcomes; if persistence or transport itself fails, a safe HTTP error may be necessary. Client should refresh history before retrying uncertain mutations. Tool-level errors are distinct from HTTP errors, and ordinary tool rejections do not automatically fail the entire turn.

## 10. Internal tool contracts (not REST endpoints)

All tools use Pydantic-validated arguments and projected outputs. Resolve customer identity from trusted execution context, not model-generated arguments. Model-visible inputs for the three customer tools are empty objects. The graph enforces allowed names, sequential execution, bounded calls, and approval gating.

```ts
type ToolResult<T> =
  | { success: true; data: T }
  | { success: false; error: ApiError };

type RetrievedChunk = Citation & {
  category: string; text: string; score: number;
};
type SubscriptionData = {
  plan: string; monthly_price: DecimalString; currency: string;
  status: string; billing_cycle: "monthly";
  period_start: Timestamp | null; period_end: Timestamp | null;
};
type PaymentData = {
  amount: DecimalString; currency: string; date: Timestamp;
  status: string; failure_reason: string | null;
};
type ResetOutcome = ResetResult | { status: "rejected" };
```

| Tool | Input | Result data | Behaviour |
| --- | --- | --- | --- |
| `search_knowledge_base` | `{query: string}` | `{chunks: RetrievedChunk[]}` | Exact cosine retrieval, top 3, configured threshold; empty list is valid |
| `get_current_subscription` | `{}` | `SubscriptionData` | Read only, current customer's subscription and plan |
| `get_payment_status` | `{}` | `PaymentData` | Read only, latest payment by timestamp with stable tie-breaker |
| `request_password_reset` | `{}` | `ResetOutcome` | Interrupt before mutation; return real result only after approval decision |

Subscription/payment statuses reflect explicit backend enums; the final enum definitions must agree with the ORM and seed data. No payment/card secrets or unnecessary IDs are exposed. Example tool errors include `PAYMENT_NOT_FOUND`, `SUBSCRIPTION_NOT_FOUND`, `INVALID_TOOL_ARGUMENTS`, `UNKNOWN_TOOL`, and `PROVIDER_UNAVAILABLE`. A rejected reset is a normal result, not an infrastructure error. Never send the model a successful reset result before database execution. Validate cited chunk IDs against retrieved sources for the current run before persisting assistant citations.

## 11. Contract acceptance checks

- Demo login and session switching correctly scope all customer resources; direct requests for another customer's IDs return 404.
- Both normal chat and mixed payment/knowledge queries return persisted messages; citation IDs are validated.
- Password-reset chat returns a backend-generated pending card before any reset record exists. Refresh restores it. Approve and reject work through the same endpoint; duplicate or concurrent submissions cannot duplicate the mutation.
- A committed reset remains visible if final response generation fails.
- Knowledge CRUD synchronizes embeddings transactionally; failed replacement leaves existing data unchanged.
- Feedback is linked to the correct owned assistant response and can be updated.
- Invalid inputs, active runs and provider failures return typed safe errors. Frontend derives state from actual API responses, not simulated successes.
- FastAPI OpenAPI documents the implemented endpoint paths, request/response schemas and error responses. Reconcile this contract with the actual implementation before submission.
